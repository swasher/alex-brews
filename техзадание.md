# Coffee Journal — Technical Specification

## 1. Project overview

Build a personal coffee website with a lightweight, integrated content management system.

This is a personal project, not a commercial platform, e-commerce website or multi-user application.

The website has three main sections:

1. **My Coffee** — a personal collection of purchased and tasted coffee, with photographs, origins, roasters, tasting notes and personal comments.
2. **My Equipment** — coffee equipment, grinders, brewers, accessories and descriptions.
3. **About Me** — personal information, coffee interests and related content.

The owner must be able to create, edit and delete content directly from the public-facing website.

There must be no separate CMS application or administrative dashboard.

### Main priorities

- Excellent editorial design and typography.
- Photography-oriented presentation.
- Fast page loading.
- SEO-friendly server-rendered content.
- Excellent mobile experience.
- Minimal client-side JavaScript.
- Simple content editing.
- Minimal infrastructure and maintenance.
- Clear, maintainable architecture.

The project will be developed primarily using AI coding agents. Favor established libraries, straightforward implementation and minimal custom infrastructure.

## 4. Rendering architecture

Use Astro SSR on Cloudflare Workers.

Configure Astro with server rendering as the default output mode.

All pages containing Firestore-backed content must use on-demand SSR.

Do not use:
- Static site generation for dynamic content.
- `getStaticPaths()` for Firestore-backed content pages.
- Build-time content snapshots.
- Client-side-only rendering of public content.

Static prerendering is allowed only for genuinely static assets or pages that do not depend on editable content.

### Important requirements

- Every public content page must receive its content from Firestore during server-side rendering.
- Changes must become visible without rebuilding or redeploying the application.
- Dynamic HTML responses must not be served from a stale CDN cache.
- Use appropriate cache-control headers for dynamic pages.
- Static assets and public images may use long-lived caching.

The initial implementation should favor correctness and freshness over aggressive caching.

## 7. Database and content models

Use Firebase Cloud Firestore.

Use three logical content collections:

- `coffee`
- `equipment`
- `siteContent`

Firestore document IDs should be the primary identifiers. Do not duplicate IDs inside documents unnecessarily.

### 7.1 Coffee

Collection: `coffee`

Fields:

- `slug` — unique URL identifier.
- `name` — coffee name.
- `roaster` — roastery.
- `country` — country of origin.
- `region` — region.
- `farm` — optional farm or producer.
- `variety` — optional coffee variety.
- `processing` — processing method.
- `altitude` — optional altitude.
- `roastLevel` — optional roast level.
- `roastDate` — optional date.
- `purchaseDate` — purchase date.
- `openingDate` — optional opening date.
- `rating` — optional personal rating, numeric 1–10.
- `description` — personal description.
- `tastingNotes` — array of strings.
- `image` — primary image reference.
- `gallery` — optional array of image references.
- `createdAt` — Firestore timestamp.
- `updatedAt` — Firestore timestamp.

Most descriptive fields must be optional.

The owner must be able to add a coffee with only a name and photograph, without filling in a large form.

### 7.2 Equipment

Collection: `equipment`

Fields:

- `slug`
- `name`
- `brand`
- `model`
- `category`
- `description`
- `purchaseDate`
- `image`
- `gallery`
- `sortOrder`
- `createdAt`
- `updatedAt`

All non-essential fields should be optional.

### 7.3 Site content

Collection: `siteContent`

Use named documents:

- `homepage`
- `about`

Homepage fields:

- `title`
- `subtitle`
- `introduction`
- `featuredCoffeeIds` — optional array of references.

About fields:

- `title`
- `introduction`
- `content`
- `portrait`
- `links` — optional array of label/URL objects.

The schemas may be extended when necessary, but avoid unnecessary abstraction.

### Content formatting

Use ordinary multiline text fields for descriptions and personal comments.

Do not introduce a complex WYSIWYG or block-based rich text editor.

Render multiline content with proper whitespace preservation.

Use structured arrays for tasting notes and external links.

### Publishing model

There is only one owner and all content is intended to be public.

New records become publicly visible immediately after saving.

Do not implement drafts, approval workflows, publication scheduling or a trash system.

## 8. Authentication

Use Firebase Authentication.

Implement a single administrator account.

### Authentication requirements

- Email/password authentication.
- No public sign-up interface.
- Administrator account is created manually in Firebase Console.
- Administrator UID is configured explicitly.
- No roles or multi-user permission system.
- No separate authentication application.

The login interface should be accessible from the public website through a discreet entry point.

Use Firebase's official browser SDK for authentication.

The application must not trust client-side authentication state for server-side authorization.

### Administrator identity

Configure:

`ADMIN_UID`

Use this UID in:
- Firestore Security Rules.
- Cloudflare Worker authorization.
- Administrative UI visibility checks.

The administrator's UID is the only authorized identity.

### Contextual authentication behavior

When the administrator is authenticated:
- Show editing controls on relevant pages.
- Show add-content controls on collection pages.
- Allow image uploads and deletion.

When unauthenticated:
- Hide all editing controls.
- Show only the public website.

Client-side visibility checks are for UI purposes only. Actual authorization must always be enforced by the backend or Firestore Security Rules.

- Be generated from the corresponding content model.

- Support text, multiline text, numbers and dates.
- Support image upload and replacement.
- Validate input.

## 10. Image storage and delivery

Use Cloudflare Images directly.

Do not use:
- Firebase Storage.
- Cloudinary.
- R2 in the initial implementation.
- External image hosting.

Use Cloudflare Images for:
- Original image storage.
- Responsive image variants.
- Image optimization.
- Image delivery.
- Image deletion.

### Upload workflow

1. Administrator selects a local image.
2. Browser requests an upload URL from a protected Cloudflare Worker endpoint.
3. Worker validates the administrator's Firebase ID token.
4. Worker requests a Direct Creator Upload URL from Cloudflare Images.
5. Worker returns the temporary upload URL and image ID to the browser.
6. Browser uploads the image directly to Cloudflare Images.
7. After successful upload, the image ID and alternative text are saved in Firestore.
8. Public pages construct delivery URLs using the configured Cloudflare Images account hash and variant names.

The Cloudflare API token must never be exposed to the browser.

Use the Direct Creator Upload API.

### Image requirements

- Support JPEG, PNG and WebP.
- Provide image previews before saving.
- Support replacing the primary image.
- Support optional galleries.
- Support image deletion.
- Validate image type and size.
- Store alternative text.
- Avoid storing redundant delivery URLs in Firestore.
- Use configured Cloudflare Images variants for thumbnails, cards and full-size images.
- Use responsive image sizes.
- Lazy-load non-critical images.

Configure image variants centrally rather than hardcoding different transformations throughout the application.

### Image lifecycle

When replacing an image:
1. Upload the new image.
2. Update the Firestore record.
3. Delete the old image only after the database update succeeds.

When deleting a record:
1. Delete the Firestore record.
2. Delete its associated Cloudflare Images objects.

Handle failures without leaving the database referencing deleted images.

If an upload succeeds but saving the record fails, provide a cleanup mechanism for the orphaned image.

## 11. Backend endpoints

Use Astro server endpoints running on Cloudflare Workers.

Keep the API small and focused.

Suggested endpoints:

- `POST /api/media/upload-url`
- `DELETE /api/media/[imageId]`

The upload endpoint must:
- Require a valid Firebase ID token.
- Verify the administrator UID.
- Request a Cloudflare Images Direct Creator Upload URL.
- Return only the required upload information.

The delete endpoint must:
- Require a valid Firebase ID token.
- Verify the administrator UID.
- Delete only the requested image through the Cloudflare Images API.

Do not implement a general-purpose REST API for content CRUD unless a specific technical requirement justifies it.

Content creation and editing should use the Firebase Web SDK directly, protected by Firestore Security Rules.

## 12. Firestore access strategy

Use two access paths.

### Public SSR reads

Astro server-side code reads public content through the Cloud Firestore REST API.

Use ordinary HTTPS requests from Cloudflare Workers.

Do not rely on a Node.js-specific Firebase Admin implementation.

Public SSR requests must return fresh Firestore data.

### Administrative writes

Use the official Firebase Web SDK from authenticated React components.

Create, update and delete operations must be authorized by Firestore Security Rules.

This keeps the authorization logic close to the database.

### Authentication and authorization

For Cloudflare Worker endpoints requiring administrator privileges:

- Receive the Firebase ID token from the authenticated browser.
- Verify the token using a Cloudflare Workers-compatible implementation.
- Retrieve and validate the actual Firebase UID.
- Compare it against `ADMIN_UID`.

A possible implementation is Firebase Authentication's documented `accounts:lookup` REST endpoint, which accepts an ID token and returns the corresponding user identity.

Alternatively, use a compatible JWT verification library with Google's public signing keys.

Do not use Firebase Admin SDK by default.

Do not introduce service account credentials merely to simplify Firestore access.

If a server-side Firebase library is proposed, first verify its compatibility with Cloudflare Workers and explain why it is necessary.

## 13. Firestore Security Rules

Security must be enforced at the database level.

Because all content is public:

- Anonymous visitors may read content.
- Only the configured administrator UID may create records.
- Only the configured administrator UID may update records.
- Only the configured administrator UID may delete records.

No client-side checks may substitute for these rules.

Example authorization principle:

`request.auth != null && request.auth.uid == ADMIN_UID`

Implement complete Firestore Security Rules for all three collections.

Test the rules using the Firebase Emulator Suite.

Never use permissive development rules in production.
